## 一、一句话版（项目标题下一行）

**Online Mall｜B2C 在线商城 + AI 智能客服**（FastAPI · MySQL · Redis · ChromaDB · Vue3，
个人项目，2026.07–2026.09）

> 前后端分离的完整交易闭环（SKU 下单 → 模拟支付 → 发货 → 退款审核）＋ 基于
> LangChain + BGE + BM25 + 交叉编码器重排的 RAG 智能客服；118 个后端测试 / 10 个
> 端到端测试，一条命令从裸机部署到线上（含自动 HTTPS 与部署自检）。

## 二、四条要点版（简历正文）

> 挑 3 条放进简历即可。**如果是投 AI 应用开发 / AI 全栈岗，务必保留第 2 条和第 4 条**
> ——前者证明你会做 RAG 且能用数据证明效果，后者证明你按线上系统的标准做 AI，
> 而不只是调通了一个 API。第 1、3 条适合投后端 / 全栈岗。
> 若岗位强调「全栈」，把第 3 条里的前端部分展开（见下方补充段）。

- **交易正确性（并发）**：用 `UPDATE ... WHERE stock >= ?` 的条件更新 + `rowcount`
  判断替代「先查再扣」，解决超卖；同一思路用于订单状态机做乐观并发控制。
  在**真实 MySQL/InnoDB** 上实测：8 线程抢 3 件库存恰好成交 3 单，同一订单 5 次并发
  支付恰好成功 1 次，失败原因被严格限定为业务错误（避免"恰好 3 单"是别的 bug 蒙对）。

- **检索效果（AI）**：自建 22 篇知识文档 + **51 条评测集**（31 条是口语化改写，并刻意
  加入近义干扰文档），在同一套评测、同一条线上代码路径上做出三级提升：
  纯向量 recall@1 84.3% → **BM25 混合检索 90.2%** → **再加交叉编码器重排 92.2%，
  recall@3 达到 100%**。评测与线上生成调用同一个 `retrieve()`，不是各写一份。

- **工程质量与交付（工程化）**：118 个 pytest 用例（覆盖率 77%）+ 10 个 Playwright 端到端用例
  （真浏览器、断言控制台零报错、含 375px 移动端视口，且已进 CI）；
  Redis 缓存（含击穿/穿透/雪崩三道防护）、全站限流、分布式锁，Redis 不可用时自动降级；
  request_id 结构化日志 + Prometheus 指标 + 9 条告警规则 + Grafana 看板；
  迁移可回滚（有真实 MySQL 往返用例）；
  GitHub Actions 每次提交都构建镜像并校验三层 compose 的合并结果；
  **一条命令从裸机部署到线上**（`deploy/bootstrap.sh` 负责装 Docker、生成随机密钥、
  预热模型、起服务、自检；HTTPS 由 Caddy 自动签发续期）。

- **可回滚的部署 + 依赖安全治理（交付与运维）**：迁移前自动备份（迁移里有真实的
  `DROP COLUMN`，失败即数据不可恢复），配 `backup.sh` / `rollback.sh`——
  备份产物做 `gzip` 完整性与 sha256 校验、回滚前再给当前库存一份快照；
  实测「转储 → 校验 → 恢复到临时库 → 比对表数与行数」全流程通过（15 张表、
  products 65 行一致）。**没实测过恢复就等于没有备份。**
  依赖侧接入 `pip-audit` 与 Dependabot，用**基线模式**而非全量卡死：
  新引入的漏洞立即让 CI 失败，23 条存量漏洞逐条登记不升的理由与解除条件。
  累计把漏洞从 **39 条治理到 23 条**：`python-jose` → PyJWT 消掉 5 条；
  LangChain 生态整组升级（0.3.13→0.3.30，含 `langchain-huggingface` 0.1.2→0.3.1）
  再消掉 6 条——后者 1.x 与 langchain-core 1.x 绑定、与本项目不兼容，
  **只有整组升才会落到匹配 0.3.x 的 0.3.1**，依赖解析器不会主动选它。
  两条「踩过才知道」的教训：换更活跃的库不等于更安全（PyJWT 2.10.1 自带 17 条 CVE）、
  以及「只防自己写的代码、不防第三方依赖」是典型安全盲区。

- **Schema 一致性（工程严谨性，适合讲「你怎么保证正确」）**：发现测试用
  `create_all` 建表、不走迁移，导致「迁移建出的库」与「测试验证的库」是两套 schema，
  功能测试全绿但漂移测不出来。用 Alembic `compare_metadata` 比对出 **10 处差异**，
  其中外键缺失（可写入不存在的 SKU）与「`users.email` 唯一约束只存在于开发库」有真实
  数据风险。修复后把比对写成零容忍测试，并用变异验证确认它会红。
  **一个 `create_all` 的便利，代价是整个测试套件验证的不是要上线的那套 schema。**

- **AI 链路可观测（AI 工程化）**：给 RAG 全链路补上原本**完全缺失**的埋点——
  改写 / 检索 / 重排 / 首 token / token 消耗分阶段计时，每轮问答输出一条结构化日志
  （`retrieval_ms`、`best_score`、`ttft_ms`、`prompt_tokens`…），把
  「慢在哪、为什么答不上来、花了多少钱」从“重启试试”变成“看一眼就知道”。
  检索结果按 `hit / all_below_threshold / empty_index / no_candidates` **四类分开统计**
  ——因为四者的处置方式完全不同，混成一个「没结果」就永远查不出问题。
  配 4 块 Grafana 面板 + 3 条 AI 专属告警，专门盯「不报错但答得越来越差」的静默劣化。
  实现中发现并修复了两个「说了却没做到」的隐性缺陷：JsonFormatter 只白名单 4 个字段
  导致业务字段被静默丢弃（埋了点却看不到），以及 404 时 label 回退原始路径
  使 label 基数防护形同虚设。

- **前端工程化（全栈向，可替换第 1 条）**：Vue3 + Vite 双入口（商城 / 后台），
  Element Plus 按需引入；**24 个 vitest 单测**覆盖 SSE 流式分帧状态机
  （跨 chunk 截断 / 多帧粘包 / 新旧协议混用）与 axios 拦截器错误分流
  （401 跳登录、登录接口例外、silent 语义）——这两块一出错表现为「AI 回答缺字」
  「登录失败冲掉表单」，真实环境极难复现，用单测构造任意分片是最合适的验证方式；
  **11 个 Playwright e2e** 跑在生产构建产物上、断言控制台零报错，
  并含 **375px 移动端 project**（断言无横向溢出、客服窗完整在视口内）；
  统一 `AsyncState` 三态组件消除「加载中/空/失败」三者同貌的问题。

## 三、STAR 详版（面试展开用）

**背景**：想做一个能真正说明问题的项目——不是又一个 CRUD 商城，而是把
「电商交易里最难对的地方」和「AI 应用里最容易糊弄的地方」都做一遍。
这两个正好是：并发下的库存与状态，和检索效果到底有没有提升。

**做了什么**：

1. **交易链路**：14 张表建模（用户/商品/SKU/购物车/订单/退款/Banner/知识库/会话/评测），
   订单状态机白名单校验，金额全程 `Decimal`，下单时保存地址与商品快照。
2. **并发正确性**：所有状态流转都改成条件 UPDATE + `rowcount`，并在真实 InnoDB 上
   写多线程用例验证——不只是"在 SQLite 上跑过"。
3. **RAG 链路**：切片 → 本地 BGE 向量化 → **向量 + BM25 混合召回** →（可选）交叉编码器
   重排 → DeepSeek 流式生成 → SSE 推前端；多轮会话做 Query 改写，历史落库。
4. **离线评测**：自建评测集，用真实模型跑召回率，把"效果"变成可回归的数字。
5. **工程化与交付**：Redis 缓存/限流/分布式锁 + 独立 worker、结构化日志与指标、CI、
   Compose、端到端测试；再把「部署」也写成了代码——一条命令从裸机到线上，
   配置校验、模型预热、部署自检、演示数据重置各一个脚本。
6. **AI 链路可观测**：交易链路早就有指标，AI 这条主角链路却一条都没有。补齐后
   每轮问答一条结构化日志，把改写/检索/首 token/token 四段耗时与检索质量
   （命中数、top-1 分数、结果分类）串在同一行；配 4 块面板 + 3 条 AI 告警。

**结果**（全部可复现）：

| 维度 | 数字 | 复现命令 |
|---|---|---|
| 并发防超卖 | 8 线程抢 3 件 → 恰好 3 单 | `pytest -m mysql -v` |
| 支付幂等 | 5 次并发支付 → 恰好 1 次成功 | 同上 |
| 检索召回 | recall@1 84.3% → 90.2% → **92.2%** | `pytest -m rag_quality -s` |
| 尾延迟 | P99 51ms → **23ms**（开缓存） | `locust -f loadtest/locustfile.py` |
| 测试 | 118 后端 + 10 端到端，覆盖率 77% | `pytest --cov=app` / `npm run test:e2e` |
| 前端体积 | dist 1579KB → **762KB** | `npm run build` |
| 部署 | 裸机 → 可访问站点 **1 条命令**，含 8 步自检 | `sudo bash deploy/bootstrap.sh` |
| AI 可观测 | 单轮问答定位到「9.2s 花在模型冷启动」 | 看一条 `AI 对话完成` 日志 |

**收获**：最值钱的不是这些数字，而是十个**反直觉的结论**（见第四节），
它们都是被数据打脸之后改出来的。

## 四、可以主动讲的十个负向结论

> 面试时讲"我做了 A 然后效果变好"很常见，讲"我做了 A、数据显示更差、于是我回滚了"
> 反而更能说明你会用数据做判断。这十条都有代码/注释/测试为证。

1. **BGE 的指令前缀对 v1.5 有害**：按 v1 的用法给 query 加前缀，命中率不变但平均余弦
   距离从 0.357 劣化到 0.401，于是回滚并把结论写进注释。
2. **`BM25Okapi` 的 IDF 会变负**：某个词出现在超过一半文档里时 IDF 为负，
   命中文档的得分反而低于完全没命中的文档（后者是 0）。项目的知识库刚好充满
   "商品""订单""配送"这类高频词，于是在小语料上直接失效 → 改用 `BM25Plus`。
   这是被一条断言抓出来的，不是看文档看出来的。
3. **模型缓存的命名撞车**：评测脚本用 `"bge" in 路径` 找 Embedding 模型，而后来下载的
   重排模型 `bge-reranker-base` 也含 "bge"，于是它被当成 Embedding 加载，
   **向量召回从 84.3% 掉到 3.9%**。不报错、只是数字变难看——没有先建基线的话，
   很可能被误判成"加了重排反而变差"而回滚一个正确的优化。
4. **简单评测集会虚高分数**：20 条 / 10 篇时纯向量 recall@1 有 90%，扩到 51 条 / 22 篇
   并加入近义干扰文档后掉到 84.3%。**先扩评测集、再做优化**，否则"提升"可能只是
   过拟合了小样本。
5. **测试也会"假通过"**：端到端用例里我把搜索参数名写成了 `?keyword=`，而页面读的是
   `?q=` —— 参数被忽略、页面列出全部商品，于是「至少有一张卡片可见」这条断言**永远成立**。
  它一直是绿的，直到真实使用时发现搜索不好用才暴露。**断言必须能失败**，
  写完之后要反问一句："这条用例在功能坏掉时会红吗？"
6. **搜索的补丁会越打越多**：用户反馈「搜鞋子没结果、搜鞋才有」，我先写了一条
   「去掉名词后缀」的规则；紧接着就得为「哪些词不该截断」再加一份例外表——搜「电子」
   会被截成「电」，实测一次性带回充电宝、鼠标、耳机等 7 条不相关结果。
   于是停下来重做：把查询理解抽成一层，三类差异分开治理——**形式差异**（空格/连字符/
   大小写/全角/容量单位）走统一归一化管道，**分词差异**交给 jieba，**用词差异**只能靠
   数据（独立的同义词表，加词只加一行），外加「AND 为空才退化为 OR」的兜底。
   **判断一个修复是补丁还是解法：看它是不是只让手头这个例子通过，还是让整类例子都不再需要特殊处理。**
7. **「一键部署」这句话，之前从来没有任何东西验证过**：README 里写着 `docker compose up`
   能起全栈，但 CI 只跑 python / npm，**从来不构建镜像**——Dockerfile 写错、compose
   变量拼错、nginx 配置语法错，全都要等到真正部署那一刻才炸，而那正是最不该出问题的时刻。
   **凡是写在文档里的能力，都得有一个自动化步骤去证明它**，否则它只是一句愿望。
   现在 CI 多了「构建两个镜像 + 解析三层 compose 合并结果」的 job，而且校验脚本本身
   也要反向验证（故意喂坏配置，断言它**必须**被拒绝）——只做正向用例的话，
   校验逻辑哪怕一直返回 0 也发现不了。
8. **CI 全绿不等于部署可行**：镜像能构建成功，不代表它在**目标机器**上能用。
   后端依赖里的 torch 一直默认装的是 CUDA 版，连带 `nvidia-cudnn-cu13`(553MB)、
   cublas、cufft 等合计 3~4GB 完全用不到的库，镜像 8GB 左右——GitHub 的机器下载快、
   磁盘大，所以 CI 一直绿灯；换到一台 2 核 2G、20G 磁盘的学生机上，光构建就可能把盘写满。
   钉成 CPU 版之后镜像回到 1.5GB 级。**结论：验证要在目标环境里做，
   不是在有资源的地方做。**
9. **「注释里写了正确做法，代码里却没做到」是最该优先查的地方**：
   `metrics.py` 的模块文档明确写着「标签要用路由模板，不能回退原始路径，否则
   label 基数会炸」——而代码恰恰在 404 时回退到了原始路径。同类问题还有一处：
   `JsonFormatter` 只白名单了四个字段，导致新埋的业务字段全被静默丢弃，
   **「埋了点却看不到」比不埋更糟**，因为你以为已经有了。
   这类缺陷的特征是**作者知道正确做法、只是没做到**，往往是被别的事情打断；
   它躲得过所有测试（不报错、不影响功能），只能靠「把实现和注释对照着读」发现。
10. **AI 链路出了怪问题，先加指标而不是先重启**：我遇到过一次「服务跑久了开始
    答非所问、重启就好」的现象，当时没有任何埋点，只能靠猜。补齐埋点后再复现，
    一行日志就给出了答案——`retrieval_ms: 9156`，九秒全花在 BGE 模型的冷启动加载上，
    不是检索逻辑有问题。**没有观测能力时，「重启一下」是唯一手段；
    有了之后，同一类问题的定位成本从半小时降到十秒。**

## 五、容易被追问的点与答法

| 追问 | 答的核心 |
|---|---|
| 缓存一致性怎么保证？ | TTL 60s + 写路径主动失效；库存允许秒级陈旧，因为真正防超卖的是下单事务里的条件 UPDATE。用 `SCAN` 不用 `KEYS`。 |
| Redis 挂了怎么办？ | 200ms 超时 + 30 秒熔断，降级为无缓存、不限流，只丢能力不丢业务；代价是没有本地多级缓存，降级期内读会直接打库。 |
| 为什么限流用固定窗口？ | 两条命令、够用；代价是窗口边界可能两倍突发。秒杀才需要令牌桶。 |
| 为什么不用 Celery？ | 只有一个定时任务，拆成独立 worker + Redis 锁已经解决多副本问题；上量或任务变多再换。 |
| 关单任务加锁是为了什么？ | **不是为了正确性**（任务本身幂等，条件 UPDATE 已保证），而是避免 N 个副本重复扫表、并让定时任务有唯一实例。 |
| SQLite 上测并发不行吗？ | SQLite 把写整体串行化，永远测不到 InnoDB 的行锁与条件更新语义；所以单独一套真实 MySQL 用例，且不能吞异常。 |
| RAG 为什么不用 LangChain 现成的 retriever？ | 评估锚点要在自己代码里。抽一层 `retriever`，评测与线上生成调同一个函数，改了检索评测就会动。 |
| 重排为什么默认关？ | 多下 1.1GB 模型、每条问题多 0.6s CPU；收益是 recall@3 98%→100%。值不值取决于场景，所以做成开关而不是替使用者决定。 |
| **AI 答得慢，你怎么定位？** | 不要用总耗时判断。拆成四段：改写 / 检索 / 首 token / 生成，每段一个直方图。用户感知的是**首 token** 而不是总耗时。我的实测里总耗时 14.5s 中，检索占 9.1s——那不是检索慢，是模型冷启动在加载。 |
| **AI 答不上来，是知识库没有还是阈值太严？** | 把「没结果」拆成四类分别计数：`empty_index`（索引没同步）、`all_below_threshold`（阈值太严或知识库缺内容）、`no_candidates`（没召回）、`hit`。四者的处置方式完全不同，混在一起就永远查不出来。 |
| **怎么知道 AI 效果变差了（而不是突然挂了）？** | 看 `rag_best_score` 的分布（P10/P50/P90）是否整体左移，以及平均得分趋势。这是「不报错但答得越来越差」唯一可观测的信号，也是配 AI 告警的意义所在。 |
| **大模型成本怎么控？** | `llm_tokens_total` 按 prompt/completion 分开记（单价不同），配速率告警。数据上 token 消耗几乎全在 prompt（检索片段），所以控制成本的关键是**少喂片段**（top-3 而不是 top-10）而不是让模型少说话。 |
| 部署是不是只能在你机器上跑？ | 三个脚本各管一段、都能单独拷到服务器上跑：`check-env` 在启动前拦配置、`smoke` 从用户入口走关键链路、`bootstrap` 一键装并起。CI 里对这些断言做了反向验证（喂坏配置必须被拒），证明它们不是一直返回 0。 |
| 模型 100MB，每次都重新下？ | 下到 `mall-data` 命名卷里持久化，部署脚本把它提前下好；重置演示数据时只删 MySQL 卷，模型不动。代价是首次部署仍要等几分钟，网络不通就是起不来——没绕过去。 |

## 六、不要这么写

- ❌ "使用 Redis 实现缓存" —— 谁都会写，没有信息量。
  ✅ "商品读路径加 Redis 缓存后 P99 从 51ms 降到 23ms（50 并发实测），并处理了写路径失效与 Redis 不可用时的降级"。
- ❌ "精通 LangChain / 精通 RAG" —— 容易被追着问到答不上来。
- ❌ "实现了分布式锁" 而不说清楚为什么要——会被问"你的任务不是幂等吗"。
- ❌ 只写技术栈罗列，不写结果。
- ❌ 写"参与"、"协助"这类动词——个人项目应该用"设计并实现"。
