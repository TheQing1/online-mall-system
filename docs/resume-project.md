# 简历项目描述（三版 + 证据索引）

> 用法：**一句话版**放在项目标题下面；**三条要点版**是简历正文；
> **STAR 版**用于自我介绍（30 秒）和技术面深挖（5～10 分钟）。
>
> 本文所有数字都能在仓库里复现，每节末尾给出命令。面试前建议照着命令自己跑一遍

## 一、一句话版（项目标题下一行）

**Online Mall｜B2C 在线商城 + AI 智能客服**（FastAPI · MySQL · Redis · ChromaDB · Vue3，
个人项目，2026.07–2026.09）

> 前后端分离的完整交易闭环（SKU 下单 → 模拟支付 → 发货 → 退款审核）＋ 基于
> LangChain + BGE + BM25 + 交叉编码器重排的 RAG 智能客服；113 个后端测试 / 10 个
> 端到端测试，Docker Compose 一键起全栈。

## 二、三条要点版（简历正文）

- **交易正确性（并发）**：用 `UPDATE ... WHERE stock >= ?` 的条件更新 + `rowcount`
  判断替代「先查再扣」，解决超卖；同一思路用于订单状态机做乐观并发控制。
  在**真实 MySQL/InnoDB** 上实测：8 线程抢 3 件库存恰好成交 3 单，同一订单 5 次并发
  支付恰好成功 1 次，失败原因被严格限定为业务错误（避免"恰好 3 单"是别的 bug 蒙对）。

- **检索效果（AI）**：自建 22 篇知识文档 + **51 条评测集**（31 条是口语化改写，并刻意
  加入近义干扰文档），在同一套评测、同一条线上代码路径上做出三级提升：
  纯向量 recall@1 84.3% → **BM25 混合检索 90.2%** → **再加交叉编码器重排 92.2%，
  recall@3 达到 100%**。评测与线上生成调用同一个 `retrieve()`，不是各写一份。

- **工程质量（工程化）**：113 个 pytest 用例（覆盖率 77%）+ 10 个 Playwright 端到端用例
  （真浏览器、断言控制台零报错，且已进 CI）；Redis 缓存（含击穿/穿透/雪崩三道防护）、
  全站限流、分布式锁，Redis 不可用时自动降级；request_id 结构化日志 + Prometheus 指标 +
  6 条告警规则 + Grafana 看板；迁移可回滚（有真实 MySQL 往返用例）；
  GitHub Actions 五任务流水线；Docker Compose 一键部署（多阶段镜像、非 root、HEALTHCHECK）。

## 三、STAR 详版（面试展开用）

**背景**：想做一个能真正说明问题的项目——不是又一个 CRUD 商城，而是把
「电商交易里最难对的地方」和「AI 应用里最容易糊弄的地方」都做一遍。
这两个正好是：并发下的库存与状态，和检索效果到底有没有提升。

**做了什么**：

1. **交易链路**：14 张表建模（用户/商品/SKU/购物车/订单/退款/Banner/知识库/会话/评测），
   订单状态机白名单校验，金额全程 `Decimal`，下单时保存地址与商品快照。
2. **并发正确性**：所有状态流转都改成条件 UPDATE + `rowcount`，并在真实 InnoDB 上
   写多线程用例验证——不只是"在 SQLite 上跑过"。
3. **RAG 链路**：切片 → 本地 BGE 向量化 → **向量 + BM25 混合召回** →（可选）交叉编码器
   重排 → DeepSeek 流式生成 → SSE 推前端；多轮会话做 Query 改写，历史落库。
4. **离线评测**：自建评测集，用真实模型跑召回率，把"效果"变成可回归的数字。
5. **工程化**：Redis 缓存/限流/分布式锁 + 独立 worker、结构化日志与指标、CI、Compose、
   端到端测试。

**结果**（全部可复现）：

| 维度 | 数字 | 复现命令 |
|---|---|---|
| 并发防超卖 | 8 线程抢 3 件 → 恰好 3 单 | `pytest -m mysql -v` |
| 支付幂等 | 5 次并发支付 → 恰好 1 次成功 | 同上 |
| 检索召回 | recall@1 84.3% → 90.2% → **92.2%** | `pytest -m rag_quality -s` |
| 尾延迟 | P99 51ms → **23ms**（开缓存） | `locust -f loadtest/locustfile.py` |
| 测试 | 113 后端 + 10 端到端，覆盖率 77% | `pytest --cov=app` / `npm run test:e2e` |
| 前端体积 | dist 1579KB → **762KB** | `npm run build` |

**收获**：最值钱的不是这些数字，而是四个**反直觉的结论**（下面第五节），
它们都是被数据打脸之后改出来的。

## 四、可以主动讲的六个负向结论

> 面试时讲"我做了 A 然后效果变好"很常见，讲"我做了 A、数据显示更差、于是我回滚了"
> 反而更能说明你会用数据做判断。这四条都有代码/注释/测试为证。

1. **BGE 的指令前缀对 v1.5 有害**：按 v1 的用法给 query 加前缀，命中率不变但平均余弦
   距离从 0.357 劣化到 0.401，于是回滚并把结论写进注释。
2. **`BM25Okapi` 的 IDF 会变负**：某个词出现在超过一半文档里时 IDF 为负，
   命中文档的得分反而低于完全没命中的文档（后者是 0）。项目的知识库刚好充满
   "商品""订单""配送"这类高频词，于是在小语料上直接失效 → 改用 `BM25Plus`。
   这是被一条断言抓出来的，不是看文档看出来的。
3. **模型缓存的命名撞车**：评测脚本用 `"bge" in 路径` 找 Embedding 模型，而后来下载的
   重排模型 `bge-reranker-base` 也含 "bge"，于是它被当成 Embedding 加载，
   **向量召回从 84.3% 掉到 3.9%**。不报错、只是数字变难看——没有先建基线的话，
   很可能被误判成"加了重排反而变差"而回滚一个正确的优化。
4. **简单评测集会虚高分数**：20 条 / 10 篇时纯向量 recall@1 有 90%，扩到 51 条 / 22 篇
   并加入近义干扰文档后掉到 84.3%。**先扩评测集、再做优化**，否则"提升"可能只是
   过拟合了小样本。
5. **测试也会"假通过"**：端到端用例里我把搜索参数名写成了 `?keyword=`，而页面读的是
   `?q=` —— 参数被忽略、页面列出全部商品，于是「至少有一张卡片可见」这条断言**永远成立**。
  它一直是绿的，直到真实使用时发现搜索不好用才暴露。**断言必须能失败**，
  写完之后要反问一句："这条用例在功能坏掉时会红吗？"
6. **搜索的补丁会越打越多**：用户反馈「搜鞋子没结果、搜鞋才有」，我先写了一条
   「去掉名词后缀」的规则；紧接着就得为「哪些词不该截断」再加一份例外表——搜「电子」
   会被截成「电」，实测一次性带回充电宝、鼠标、耳机等 7 条不相关结果。
   于是停下来重做：把查询理解抽成一层，三类差异分开治理——**形式差异**（空格/连字符/
   大小写/全角/容量单位）走统一归一化管道，**分词差异**交给 jieba，**用词差异**只能靠
   数据（独立的同义词表，加词只加一行），外加「AND 为空才退化为 OR」的兜底。
   **判断一个修复是补丁还是解法：看它是不是只让手头这个例子通过，还是让整类例子都不再需要特殊处理。**

## 五、容易被追问的点与答法

| 追问 | 答的核心 |
|---|---|
| 缓存一致性怎么保证？ | TTL 60s + 写路径主动失效；库存允许秒级陈旧，因为真正防超卖的是下单事务里的条件 UPDATE。用 `SCAN` 不用 `KEYS`。 |
| Redis 挂了怎么办？ | 200ms 超时 + 30 秒熔断，降级为无缓存、不限流，只丢能力不丢业务；代价是没有本地多级缓存，降级期内读会直接打库。 |
| 为什么限流用固定窗口？ | 两条命令、够用；代价是窗口边界可能两倍突发。秒杀才需要令牌桶。 |
| 为什么不用 Celery？ | 只有一个定时任务，拆成独立 worker + Redis 锁已经解决多副本问题；上量或任务变多再换。 |
| 关单任务加锁是为了什么？ | **不是为了正确性**（任务本身幂等，条件 UPDATE 已保证），而是避免 N 个副本重复扫表、并让定时任务有唯一实例。 |
| SQLite 上测并发不行吗？ | SQLite 把写整体串行化，永远测不到 InnoDB 的行锁与条件更新语义；所以单独一套真实 MySQL 用例，且不能吞异常。 |
| RAG 为什么不用 LangChain 现成的 retriever？ | 评估锚点要在自己代码里。抽一层 `retriever`，评测与线上生成调同一个函数，改了检索评测就会动。 |
| 重排为什么默认关？ | 多下 1.1GB 模型、每条问题多 0.6s CPU；收益是 recall@3 98%→100%。值不值取决于场景，所以做成开关而不是替使用者决定。 |

## 六、不要这么写

- ❌ "使用 Redis 实现缓存" —— 谁都会写，没有信息量。
  ✅ "商品读路径加 Redis 缓存后 P99 从 51ms 降到 23ms（50 并发实测），并处理了写路径失效与 Redis 不可用时的降级"。
- ❌ "精通 LangChain / 精通 RAG" —— 容易被追着问到答不上来。
- ❌ "实现了分布式锁" 而不说清楚为什么要——会被问"你的任务不是幂等吗"。
- ❌ 只写技术栈罗列，不写结果。
- ❌ 写"参与"、"协助"这类动词——个人项目应该用"设计并实现"。
